# Architecture

Mirrin is one Go binary that behaves like a resident: it is always on, it has memory, it has hands, and it asks before doing anything consequential.

## Where things live

```

                         reach, backup, restore, cloud, doctor, report, usage, memory, audit, update, uninstall, licenses

internal/persona         personalities as data (bundled Mirrin, Nyra and Pickoo; user and pack personas)
internal/identity        export/import of a twin as an archive
internal/tray            menu bar / system tray icon
```

## Identity model

A twin is the sum of four kinds of files under `~/.mirrin`, all yours:

| Part | What it is | Where |
|---|---|---|
| Persona | who it is: name, character, style, voice, wake word | `personas/*.yaml` (bundled Mirrin, Nyra, Pickoo) |
| Memory | what it knows: facts, portrait, conversations | `data/memory.db` |
| Protocols | what it does on its own | `protocols/*.yaml` and `protocols/packs/` |
| Config | how it's wired: model, channels, autonomy | `config.yaml` |

`mirrin identity export` bundles these (config without secrets) into a tar.gz readable only by its owner; `import` restores them, keeping the destination's keys, folders and API address. An archive is personal input, never shared: import accepts only settings, memory, personas and the YAML files protocols read (never tools, scripts, `remote.yaml` or tokens), refuses unsafe paths and a `protocols_dir` that holds the twin, and checks the whole archive before it changes anything. Personas and protocols are the shareable parts and travel in packs; memory and config are personal.

Keys and tokens never travel in an identity export. An encrypted backup (`mirrin backup`, `docs/backup-format.md`) carries them, readable only with the owner's 12 words (see Secrets below).

## The loop

```
chat ──► daemon.handle ─► mailbox ─► agent.Handle
                                       │
                       ┌───────────────┼──────────────────┐
                       ▼               ▼                  ▼
                 memory.History   persona + facts     tools.Specs
                       └───────────────┼──────────────────┘
                                       ▼
                               llm.Provider.Complete
                                       │
                          stop == tool_use?  ──no──► reply
                                       │yes
                                       ▼
                             approvals.Policy.Decide
                        allow ─► tool.Run ─► result ─► loop
                        ask   ─► approvals row ─► "PENDING_APPROVAL" result ─► loop
                        deny  ─► error result ─► loop
```

Every message in and out, every tool call and every approval is stored. A conversation is keyed by `channel:chatID`. One turn runs at a time in each conversation; different conversations run concurrently. The terminal and voice answer in line, since the person is waiting on the spot; chat apps drop each message in its conversation's mailbox and return at once (see Channels).

## Approvals

Tools declare a risk: `read`, `write`, `dangerous`, and a tool may raise it for one call (a click on a pay button, a file under `~/.ssh`). Config maps each risk to `auto`, `ask` or `never`, with per-tool overrides; `always_allow` never covers a dangerous call. When a call needs approval the agent writes a row to `approvals` with the exact input and a summary the owner can check whole (a `tools.Summarizer` writes its own: the full command, script, or a protocol's schedule and prompt), returns a tool result telling the model to explain and wait, and the model tells the user. A tool that can tell a call could never work (a `tools.Checker`: a schedule that can't run) refuses it before anyone is asked. The user replies `yes N`; the daemon claims the approval (a conditional update from pending, so an approval answered twice, by a double click or the orb and the screen together, is carried out once), runs the stored call and gives the model the result as a system-framed user turn so it can report the outcome. The model never runs a gated tool directly.

**Where it may be decided** (`answerable` in `internal/daemon/approvals.go`). Every approval belongs to a home conversation: the chat it was raised in, or the chat that started the task, protocol or watcher run that raised it. It can be decided there, on the presence screen (cards or composer), and in the owner's chat when the home can't be reached (a task started from the terminal reports to the phone) or when the request was forwarded there because its own channel couldn't deliver it (`forward.go`). Two rules keep that safe and free of deadlocks:
- A channel whose sender can be forged (`forgeable`: IRC, where anyone can take a nick, and email, where From is whatever the sender typed) decides only the approvals raised in its own conversation. The owner answers anything else on the presence screen, and the twin says so.
- A request raised on the screen is decided there (a task's step aside), so no two chats ever wait on each other's turn.

**What a bare yes means.** A bare "yes" (or "Yes.", "ok, go ahead", 👍) decides only the one approval the twin's latest message to the owner asked about: raised in that turn, or quoted the way the twin is told to ask ("reply "yes 12""), never a number in passing, in a web page or in an email. It must be answered after the question, within 30 minutes, for an approval under 30 minutes old; otherwise the twin asks which one, showing each request as stored, and a yes to that goes ahead. While a notice is on its way to a chat, a bare yes there isn't taken for the question before it.

**Strangers** (`internal/daemon/strangers.go`, `internal/agent/strangers.go`). With `reply_to_others` on, a turn for anyone but the owner is marked as theirs from start to finish, including the turn that follows a decision for them. The model is told the sender is not the principal, none of the owner's memory (facts, portrait, `about`) is in the prompt, and every tool call, even a read, needs the owner, one waiting request per chat at a time. The requester is stored with the approval before anyone hears of it. The owner is told in their own chat, with the requester quoted and marked "not you", and answers with `yes N` only, from one of their own chats (their chat on a channel, the terminal, voice) or the screen, never from another shared chat and never with a bare yes. The person who asked hears the outcome; the owner's history keeps a line about the request, not the requester's words. In a shared chat, requests the twin makes for someone else need `yes N` as well.

**Answers in other forms** (`internal/daemon/answers.go`, `alwaysallow.go`, `interrupt.go`, `approvals_expiry.go`). Every approval keeps the risk it was asked at, a hash of its input (a row whose input changed after it was asked is never run) and who decided it: a paired device is named, whether it decided on the screen's cards, with `yes N` or in its own words. The owner may answer in their own words ("the landlord one"), which the model settles with `resolve_approval`, held to the owner's literal message; a dangerous request still needs `yes N`, and a transcribed voice note never approves. "Yes, always" adds the tool to `autonomy.always_allow` after a one-line check, only from the owner's own chat (not voice, email, IRC or a shared chat, and never for dangerous tools or the `neverAlways` set: writing tools or routines, packs, browser clicks, private memories); a watcher's run, whose input is others' email and invites, ignores `always_allow` for anything that changes something. Requests lapse after 3 days (a sweep on the heartbeat, and a check when any answer arrives). "Stop" on any channel, spoken ("Hey Mirrin, stop"), in a voice note or from the menu bar cuts what runs at once and turns down what that turn had asked, unless the stop came from a device that may not approve. A device paired without `approve` can't decide anything, in any form.

**Carrying it out.** An approved action runs detached from whoever approved it, so closing the page doesn't cut it short; a task's step goes back through its task; a browser action runs only if the browser is still on the page it was asked on, and is marked expired if not. A live phone call runs in `voice:phone#call-<id>`, nobody's chat: what it needs approved is put to the owner in their chat and answered there, and nothing about it is read out in the room.

## Memory

Single SQLite file (`modernc.org/sqlite`, pure Go). Tables: `facts`, `messages`, `reminders`, `approvals`, `audit`, `kv`, `model_usage` (tokens per day, model and kind of work; no content), and `schema_version`. Every schema change is a registered migration (`memory.Register`, ordered by version, run once inside one `BEGIN IMMEDIATE` transaction and recorded in `schema_version`), so any older file is brought up to date the same way; a package adds its own columns from its own file with `memory.AddColumn`. `Open` runs `PRAGMA quick_check` first: a damaged file stops the twin with a `DamagedError` that names the newest backup, and `mirrin memory restore` pauses the background service, holds the home's claim (`data/antbot.lock`), copies and checks the backup beside `memory.db`, then swaps it in with one rename, keeping the damaged file and its journal aside (never deleting them), so a twin that starts part-way through never finds the file missing. The activity log is kept 90 days and its quotes, like long tool results in chats, are cut short after 30 (`retention:` in config). Facts are injected into the system prompt on every turn so the twin never has to "remember to recall": all of them while they fit in a budget (about 12,000 characters), past that the ones that share words with the message and then the newest, and the model is told when it isn't seeing everything. The stable persona is cached at the provider; the time and facts are in a second, uncached system block. Forgetting a fact removes it and every copy of its wording the twin kept (the remember call, recall results, approvals, the audit log, and the twin's own replies for a fact long enough to be unmistakable), zeroes the rows on disk, and scrubs the same way the daily copies in `data/backups` (a week of them, taken by the heartbeat) and the copies an identity import saved of the memory it replaced. Encrypted backups already written keep it until retention removes them; a forget asks for the next one soon. A few `kv` keys belong to the machine rather than the twin (`memory/machine.go`: when the scheduler last looked, a pause, a standby's pause): a restore or import keeps this machine's, so nothing due before it is made up again. Background work runs in scratch conversations (`telegram:1#protocol-…`, `#task-…`, `#watch-…`, `#call-…`); `memory.LiveKey` is the chat behind one, where what it leaves for the owner (a reminder) belongs, and scratch history is pruned after 48 hours unless an open task or a waiting approval still needs it.

## Logs, reports and cost

Every command logs to `~/.mirrin/logs/mirrin.log` (`internal/logs`): rotated at 5 MB with three old files kept, secrets taken out of every record (saved keys, the API token, anything shaped like a credential, and never a Recovery Kit word), and crashes copied to `logs/crash.log`, so the double-clicked menu bar app leaves a record too. `uninstall` and `restore`, which delete or move the home, open no file in it. Under the service manager only warnings, errors and the "online" line also go to standard error. `mirrin report` writes a problem report for the owner to read and share: versions, self-checks, channel states, memory counts, model spend, the config with secrets and personal details hidden, and recent log lines; never messages, facts or keys. Each model call's tokens are added to `model_usage` by the agent; `mirrin usage`, the "Model spending" self-check and `Daemon.Spend` price them from a small table (`llm.PriceBook`, overridable under `usage.prices`) as US-dollar estimates against `usage.monthly_budget`; a running twin gives a desktop notice once a month at 80% of the budget and once when it is passed (`usage.notified.<month>.*` in `kv`).

## Heartbeat

The heartbeat keeps time by the wall clock: Go's timers stop while a Mac sleeps, so the scheduler looks at the clock at least every 20 seconds (sooner when a run is due) and `robfig/cron` only parses schedules. A protocol whose schedule cron can't read is skipped and logged, and never stops the others (`create_protocol` refuses one before the owner is even asked). The owner moves a routine, turns it off or on, or skips its next run in one sentence (`update_protocol`, approved in words, never cron) or on the Routines page; changing a pack's routine makes the owner's own copy, which shadows the pack's, and a skip is kept in the store until that one scheduled run (a run the owner asks for is never skipped). Each run gets its own scratch conversation. A schedule missed while asleep, or while the twin wasn't running, runs once however many runs it missed, labelled late and why; the model may reply `NOTHING_TO_REPORT` when it no longer makes sense. One more than 12 hours late is listed for the owner instead of run. Built-in upkeep catches up quietly; built-in jobs that message the owner are skipped when more than 3 hours late. Reminders fire from the same look; ones that fell due while asleep arrive together, each with its time, and one that can't be delivered is retried after 1, 5, 15 and 60 minutes, then given up with a note in the owner's conversation. A delivery that hangs is given up after 2 minutes so it can't hold up the schedule. The time zone follows the system unless the owner pinned one; when it changes the reminders tool, the calendar and email tools and the model's "Current time" follow, and the owner is told once (not while paused). A pause survives restarts, and resuming sends one summary of what waited. A reminder set during a phone call goes to the owner's chat. Protocol output goes to the owner's chat unless the model replies `NOTHING_TO_REPORT`. Background runs heal a model that had no key, as a message does, and say what's missing in plain words.

## Watchers

`internal/watch` polls sources that implement `Snapshot(ctx) map[string]string` (calendar: next 7 days by event id; inbox: unread IMAP mail by uid; Gmail: the Primary inbox, from when Google is connected, unless IMAP already watches the same address), stores the last snapshot in the key-value table, diffs, and hands a change description to the agent as a task. The sources can change while the twin runs (`Watcher.Add` and `Remove`, from `syncGoogleWatch` in `internal/daemon/google_account.go`): connecting Google or switching Calendar or Gmail on adds its source, starting from a fresh baseline, and disconnecting or switching it off removes it, with no restart. Mail is judged by when it arrived (a high-water mark), so reading mail or older unread mail coming into view wakes nothing. What senders and invites wrote goes to the model fenced as quoted information, never as instructions. The run sees none of the owner's memory, and every tool call it makes, even a read, needs the owner's yes (`always_allow` doesn't apply); it is told to say what changed in one message and offer to look further. A change the model couldn't evaluate is retried; a source that was down for a day starts from a fresh baseline. First poll only records a baseline. Paused daemons skip notifications. Each source keeps the zone it was made in: its snapshots compare times as text.

## Voice pipeline

```
mic ──sox──► wake_helper.py (openWakeWord, 80 ms frames) ──"wake"──► Interrupt() playback
                     │ captures utterance until ~1 s silence
                     ▼
      whisper (server kept warm, else whisper-cli; vocabulary prompt) ──► agent ──► reply
                                                                       │
                                     sentences ──► Kokoro/ElevenLabs (synth ahead by one) ──► play
```

Speech-to-text goes through `internal/transcribe`: the voice channel keeps a `whisper-server` loaded on a private address and falls back to `whisper-cli`, and chat voice notes (WhatsApp, Telegram, Discord, Slack, Matrix, Mattermost, Signal, iMessage) are converted and transcribed the same way, one at a time, reading `channels.voice.language` the same way. The first `mirrin voice setup` on a computer set to a language other than English picks the multilingual `small` model with the language on `auto`; otherwise it is `small.en`. "Hey Mirrin, stop" while a turn runs cuts it short (`OnStop`) rather than waiting behind it. The helper process owns the microphone and only emits an utterance file after the wake word fires (or on a "listen" command for follow-ups), so with a wake-word model nothing is transcribed unless addressed to the twin. The wake phrase is confirmed from its own clip before any acknowledgement (`wakeLoop` in `internal/channels/voice/wakeloop.go`): the detector's chime only says something was heard, and the spoken "Right." waits for whisper to confirm the name, so a false wake gets no answer to the room. A live spoken yes never approves a dangerous request, since anyone in the room can say it (`refuseAloud` in `internal/daemon/voicehooks.go`): the request goes to the owner's own chat with its number, and the twin says where. Speech out is pipelined per sentence; the current utterance's cancel function is held so a wake event can cut it off. When the chosen engine fails, the sentence falls back rather than being skipped (`internal/channels/voice/fallback.go`): ElevenLabs to Kokoro when it is installed, then to the system voice, which says it is the backup first; the owner is told once and the failed engine rests five minutes. Without the detector, or a model for the name (releases ship none; `internal/channels/voice/wakemodel.go`), the channel falls back to a silence-gated recorder plus transcript matching.

## Channels

`channels.Channel` is `Start(ctx, handler)`, `Send(ctx, chatID, text)`, `OwnerChatID()`. Thirteen transports implement it (WhatsApp, Telegram, iMessage, Signal, Discord, Slack, Matrix, Mattermost, Zulip, IRC, email, voice, terminal), all as hand-written clients over HTTP, websocket or a helper process, so adding one is a single package of a few hundred lines with no SDK dependency: connect, filter to the owner, hand text to the handler, split replies to the platform limit (`channels.SendParts`, which after a failure sends only what didn't arrive). `channels.MessagingOrder` ranks them for proactive messages. Voice and the terminal don't count there: with no messaging app, what the twin does unprompted stays on the presence screen with at most one desktop notification, and is read out loud only for a reminder or to an owner who has just been talking to it (`internal/daemon/proactive.go`). Wherever it goes, what the twin sends unprompted (a routine's result, a reminder, the watcher's news, a task's result, a tip) is also kept on the screen under Left for you, the last 12 for 18 hours (`internal/daemon/leftforyou.go`); a wall screen sees only their titles. What can wait (the watcher's news, an idea, a tip, a task's result) is held in quiet hours (`user.quiet_hours`, else `push.quiet_hours`, else 22:00 to 07:00), and all but a task's result while a calendar event is under way: it shows under Left for you marked held, with no notification, and goes out as one note when the quiet is over or with the morning briefing. A reminder, a question, an approval, a routine's result and anything the watcher marks `NOW:` are never held (`internal/daemon/held.go`). The first week's one-a-day tips skip a day with nothing for this owner (the calendar and inbox tip once both are connected, the wake word before voice is set up), and a tip's card has Thanks and No more tips, which needs the `chat` scope (`POST /screen/tips/off`, `internal/daemon/firstweek.go`).

**The owner.** Each transport marks every inbound message `IsOwner` from something a stranger can't claim: a phone number or platform user id on most. WhatsApp runs as a linked device (whatsmeow), and only the account's own "message yourself" chat counts as the owner talking to the twin; what the owner sends other people never does. Two transports have nothing like that, so they need proof. IRC recognises the owner by their services account (IRCv3 `account-tag`) or a full `nick!user@host` mask, and keys the owner's conversation by that identity, not the nick in use. Email counts mail as the owner's only when the receiving server's own `Authentication-Results` header records an SPF, DKIM or DMARC pass for them (`skills.email.auth_servers`, or a guess from the IMAP host; `internal/skills/email/inbound.go`). A message that claims the owner's conversation without that proof is dropped and logged, never answered, not even as a stranger's; for email the Channels page says why, and a transport can surface a setting to fix with `channels.Warner` (IRC warns about a mask that would accept anyone). Everyone else is ignored unless `reply_to_others` is on (see Strangers under Approvals).

**Supervision** (`internal/daemon/channels.go`). The daemon supervises every messaging channel. When `Start` returns early, the instance is closed (if it is an `io.Closer`), a fresh one is built from config and started with jittered backoff. An error wrapped in `channels.Fatal` (a rejected token, a wrong IRC password, a missing permission) stops it instead and is shown on the Channels page; if the channel had been working, the owner is told on another one. Optional interfaces: `Reporter` (real connection state for the Channels page and the health check; embed `channels.Tracker`), `Typer` and `TypingEnder` ("typing…" while a reply is worked on), `Warner` (a setting the owner should fix).

**Mailboxes** (`internal/daemon/conversations.go`). `handle` drops each chat-app message into its conversation's mailbox and returns at once, so a long turn never stalls a transport's receive loop and later messages wait their turn instead of going stale. A worker answers the mailbox in order; plain messages that piled up behind a long turn from the same sender are answered together, while commands, yes/no replies and attachments are always taken on their own. The owner's turns start at once; other people's share three slots per channel, and past a hundred waiting chats new strangers are turned away. A conversation holds up to 64 waiting messages from the owner and 64 from everyone else, so in a shared chat a crowd can't crowd the owner out; past that a message is dropped and the owner is asked once to resend. Nothing is ever sent from the transport's own receive loop (Signal can only finish a send by reading on it). Messages the twin sends on its own while a turn runs (a reminder, a task update) are recorded after that turn, in the chat they were delivered to. A transport never answers by itself: an attachment goes to the daemon as `Inbound.Media` (with any caption as `Text`) and, when the transport can fetch it, `Inbound.Attachment`, and the daemon opens it in the mailbox worker, never on the receive loop (`internal/daemon/media.go`): a voice note is transcribed and answered as "(voice note) …", a photo is fitted and shown to the model (kept 30 days under `data/media`), and anything else is answered, recorded and audited honestly. A short voice note from the owner while their turn runs is heard at once, so a spoken "stop" in it isn't stuck behind that turn.

**Delivery.** A message for the owner that its channel can't deliver falls back to the next connected channel in `MessagingOrder` (only what didn't already arrive), then to a desktop notification, and an approval that went that way can be answered where it arrived. A reply to the owner is never read out loud by the voice channel instead (a reminder with nowhere else to go is), a reply to anyone else is never redirected, and the outcome of an approval is told only in the chat it came from.

## Skills

A skill is a package exposing `Tools(...) []tools.Tool`. `tools.New(name, description, schema, risk, fn)` is all you need; `tools.WithSummary` gives a tool its own approval text, and `WithRiskFor` raises the risk of one call. Register in `internal/daemon`. Keep tool output plain text; the model reads it.

Three skills guard what they touch. `fetch_url` (`internal/skills/web/egress.go`) reaches only the public internet: every connection, each redirect included, is checked against the address actually dialled, so a name that resolves to this machine, the home network, Tailscale or a cloud metadata address is refused unless `skills.web.allow_hosts` lists it; through a proxy, every address the target has must be public before the request goes. The browser keeps to the same rule through a local guard proxy (`internal/skills/browser/egress.go`) that everything Chrome loads goes through, and that dials only the address it checked; it shares the list (`web.Allowlist`), and a change from the settings reaches both at once. The file tools (`internal/skills/system/sensitive.go`) treat keys, cloud credentials, keychains, password stores, browser profiles, `.env` files and Mirrin's own home and data as dangerous, with symlinks resolved first, so `always_allow` never covers them and the approval says why.

## Programs the twin starts

Custom tools and MCP servers run as the owner, so they get as little of the daemon as they need (`internal/procenv`). `procenv.Base` is a minimal environment: where things are (`PATH`, `HOME`, temp dirs), who is running, locale, proxy and certificate settings, where language runtimes live (`JAVA_HOME`, `PYTHONPATH`, `GOPATH`…), the desktop and session bus, `DOCKER_HOST`, and what Windows needs to start a program at all. None of it is a secret in the usual setup. A custom tool adds the variables named under `env:` in its `tool.yaml` (`procenv.With`, which looks each up in the environment, then `secrets.env`); an MCP server adds its `env` block, where `$NAME` or `${NAME}` is resolved the same way (`procenv.Expand`), so a token is passed through without being written into `config.yaml`. The daemon's own environment, where a model key or channel token may sit, is never passed on. `run_shell` is the exception: a command the owner approved runs with the daemon's own environment, so in a foreground `mirrin chat` it sees an exported model key. Anything new that starts a program for the owner should use `procenv` too.

The background service doesn't see the owner's shell, so `mirrin service install` copies what the config names and the `env:` names of the custom tools under `~/.mirrin/tools` into `secrets.env` (see Secrets).

A tool the twin wrote for itself (`author: twin` in `tool.yaml`) never runs below `write`, whatever risk it declared, so each run asks until the owner lists it in `autonomy.always_allow` (one it declared `dangerous` stays dangerous, which `always_allow` never covers): a model that could mark its own code `read` could give itself a way round every approval. A tool written by hand keeps the risk its manifest gives it.

## Model gateway

`llm.Provider` has one method: `Complete(ctx, Request) (*Response, error)`, with neutral message and block types. `llm.Anthropic` maps to the official SDK; `llm.OpenAICompat` speaks the chat-completions dialect and serves OpenAI, Gemini's compatible endpoint, Ollama and any `openai-compatible` base URL. `llm.New` resolves settings from config; `llm.Models` lists what a provider offers for the tray. `llm.Friendly` turns a provider's error into a plain sentence with the next step (bad key, out of credit, rate limit, model not pulled, Ollama not running).

## MCP

`internal/mcp` is a stdio JSON-RPC client (initialize, tools/list, tools/call). `internal/skills/mcp` wraps each server tool as a `tools.Tool` named `server__tool` with a risk level from config, so MCP tools go through the same approvals gate as built-ins. Servers start with the environment described under Programs the twin starts.

## Secrets

Keys and tokens the owner gives Mirrin live in two files, both 0600: `config.yaml` (a key pasted into `mirrin init` or a Channels card) and `secrets.env` (`KEY=value` lines; `internal/config/secrets.go`). Credentials it makes itself (`data/api.token`, `google-token.json`, paired devices' key hashes in `data/devices.json`, the WhatsApp session in `data/whatsapp.db`) stay in the home and never travel in an identity export; signal-cli keeps its own store. An encrypted backup carries `secrets.env`, `config.yaml` with its keys, the Google sign-in, `data/devices.json` and `data/tls` (and the WhatsApp session only with `backup.sessions`), never `data/api.token`. `config.Secret(name)` reads the environment first, so an exported key wins, then `secrets.env`, each time it is asked, so a key saved while the twin runs is used without a restart. The daemon never loads `secrets.env` into its own environment (every reader, the ElevenLabs voice included, asks `config.Secret`), so programs it starts inherit none of it.

`mirrin service install` copies the variables the config names (`Config.SecretEnvs`: provider keys, channel tokens, the mailbox password, the Twilio token, MCP `$NAME` references, and custom tools' `env:` names) from the installing shell into `secrets.env`. Service definitions never carry secrets: `service.Env` is `MIRRIN_HOME`, `MIRRIN_SERVICE=1`, `HOME`, `PATH` and `USERPROFILE`, and whenever `mirrin run`, `tray`, `chat`, `voice`, `init` or `service` starts, `service.TidyUnit` moves any key an older version wrote into this home's launchd plist or systemd unit into `secrets.env`, then removes it from the unit. `mirrin identity export` leaves every secret out, including passwords in URLs, `NAME=value` pairs and secret flags in MCP commands, and secret headers; import keeps the destination's own values and lists what is still to set.

## Keeping data safe

Several layers, each cheap, so one mistake doesn't lose the twin:

- **Private files.** Config, `secrets.env`, the API token, `data/devices.json` and identity archives are created 0600, and the data directory and backups 0700. `config.yaml` is read, changed and written as one edit under a lock beside it, so the menu and `mirrin backup init` saving at once don't lose each other's change.
- **One twin per home** (`internal/daemon/instance.go`). `Run` holds an OS lock on `data/antbot.lock`, so two copies never share the memory, the WhatsApp session, the bot tokens or the heartbeat. A copy started by the service manager (`MIRRIN_SERVICE=1`) waits for the lock; any other copy says the twin is already running and quits. Identity import checks the same lock and refuses while a twin holds the home.
- **Nothing half-saved.** The tray's settings are validated and the new model built before `config.yaml` is written, so a config that can't start is never saved. Identity import checks the whole archive first, saves every file it replaces in `~/.mirrin/backups/<time>`, writes each one atomically (through a symlink to a dotfiles folder, if there is one), and restores conversations through SQLite rather than over a live file.
- **Daily copies.** The heartbeat checks `memory.db` (`PRAGMA quick_check`) and copies it with `VACUUM INTO` to `data/backups` once a day, keeping seven. A database that fails the check is never copied, so a damaged file can't push the good copies out.
- **Encrypted backups** (`internal/backup`, `docs/backup-format.md`). Once set up with `mirrin backup init`, the whole twin is snapshotted every night at 03:30 (and soon after a device is paired or revoked or a fact forgotten) to iCloud Drive, a folder or an S3-compatible bucket (AWS S3, Cloudflare R2, Backblaze B2, MinIO), end-to-end encrypted with age under a key made from 12 words that are never stored; a memory that fails the check is never snapshotted. `mirrin restore` checks everything before it swaps anything, keeps the old home aside, and leaves a signed note that makes the machine the twin moved from stand by.
- **Forget reaches every copy it can.** Rows are deleted with `secure_delete` on and the WAL truncated, and the same scrub runs over the daily copies and the copies an identity import saved (see Memory). Encrypted backups already written keep a forgotten fact until retention removes them; take a new backup and prune to be rid of it sooner (`docs/backup-format.md`, "Forgetting and backups").
- **Packs change only when asked.** A pack is pinned to the commit it was installed at; `mirrin protocols update` shows the changed files and asks before applying. Packs come only from https, ssh or a local folder, and symbolic links inside one are never followed or exported.
- **One bad file is skipped.** A persona or protocol file that can't be read, or a schedule cron can't parse, is skipped and reported; everything else keeps running.

## Multi-device

The API trusts a credential by the listener the request arrived on (`internal/api/auth.go`; `docs/threat-model.md`, "Local surface"). There are three kinds. The loopback listener (`api.listen`) is this computer: the master key (`data/api.token`) works there only, and the menu's `?token=` links swap it for the browser's own `mirrin_dev` key (a browser still holding AntBot's `antbot_dev` cookie stays signed in and moves to the new name). The remote TLS listeners that `internal/reach` starts (`reach.mode`: `tailscale`, `files` or `relay`; `cloud` is reserved) take device keys only. The old plain-HTTP `api.remote` listener takes device keys and, for view, chat and approve, the old shared key while clients move onto keys of their own; it belongs on Tailscale or a LAN the owner trusts, and it can't take a passkey. The routes, ports and commands are in `docs/reach.md`.

**Remote TLS.** Every route ends TLS on this computer with a key only it holds (`internal/tlsmgr`): a Tailscale certificate for its `ts.net` name (never `tailscale serve`, whose Host-based routing another tailnet device could spoof), the owner's own certificate files, or a Let's Encrypt certificate the twin gets through its own relay tunnel (`internal/relay`), which only forwards TLS it can't read. A remote listener answers only to its own names. Pairing codes pin the listener's key, and the next key is announced ahead of a rotation. With a relay, `internal/certwatch` checks certificate transparency logs and CAA every 6 hours; a certificate this computer didn't ask for pauses approvals from other devices and signs out the ones that used the name since (`internal/reach/alarm.go`).

**Device keys.** Every device has a key of its own (`abt1_…`, only its SHA-256 kept in `data/devices.json`, `internal/devices`) with scopes (`view`, `chat`, `approve`, `admin`), which hold in chat too: a device without `approve` decides nothing, in any form. Settings pages answer on this computer only, unless `reach.admin_remote` lets an `admin` device open them from afar. `mirrin pair` asks the running twin for a single-use, 10-minute offer: an `ab2.` code for `mirrin connect` (which saves `~/.mirrin/remote.yaml`, so `chat` and `voice` post to the remote daemon), a `/pair#…` link with `--screen` or `--kiosk`, or the QR code of **Add your phone…** (`mirrin devices add`), which installs the presence screen as an app. Every new device is announced in the owner's chat. `mirrin devices`, the Devices page and `/revoke` revoke at once, deleting the device's key, its push subscription and its passkeys.

**Web Push** (`internal/push`). A paired phone that turned notifications on gets approvals, questions and security alarms on its lock screen. The daemon encrypts each message itself (RFC 8291, with its own VAPID key) and sends it straight to the browser's push service; no Mirrin server is involved. A notification carries no decision: tapping it opens the request. `push.preview` sets how much of the summary it shows, and `push.quiet_hours` never holds back approvals or alarms.

**Passkey step-up** (`internal/stepup`). A dangerous decision from any device other than this computer needs a passkey (WebAuthn: Face ID, a fingerprint or the device PIN) that signs that one request, its exact input and the decision, once, within two minutes; `reach.step_up` can ask for it on writes or on every decision, never less. A device without a passkey is refused and told to approve on the computer or with `yes N` in the owner's own chat. A passkey can be set up within 15 minutes of pairing, with one the device already has, or after `/passkey <id>` in the owner's chat, and every setup is announced.

## Cloud track

The cloud foundations are merged: `internal/relay/wire` and `internal/relay` implement the tunnel protocol and client; `cmd/mirrin-relay` routes tenant TLS streams without decrypting them. `internal/entitle` and `internal/httpsig` check signed entitlements, deny lists and control-plane requests. The nested `cloud/` module implements the control plane with billing and DNS adapters. This is implemented infrastructure, not a launched paid service.

`internal/cloud` is inert until the owner explicitly links a machine with `mirrin cloud link`. Only `cmd/mirrin`, `internal/daemon` and `internal/reach` may import it. A linked daemon refreshes its entitlement and records its requests in an egress ledger; `mirrin cloud status` and `mirrin cloud egress` read local state. Boundary and zero-egress tests keep core features independent of payment and an unlinked daemon off cloud and relay hosts. Production trust keys are not yet configured.

HTTPS reach, the installable phone app, Web Push, passkey step-up and S3 backups are in the code (see Multi-device and Keeping data safe), as is the backup target for the paid service. The paid service itself (Cloud reach and Cloud backup) is not launched: its design is [docs/cloud-design.md](docs/cloud-design.md). Nothing free today moves behind payment, and the twin never pitches the service.

## One daemon, many front ends

`mirrin run` (headless) or `mirrin tray` (menu bar) is the single long-lived process, and only one runs per home (see Keeping data safe). It opens a loopback HTTP API (`api.listen`, default `127.0.0.1:7742`; always on 127.0.0.1 at that port, whatever else it listens on) guarded by a random master key in `data/api.token`, which works on the loopback listener only (see Multi-device). If it can't listen, everything else keeps running and the health page says why; when another program holds the address, the daemon tries again every 30 seconds. `mirrin chat` and `mirrin voice` probe that API on start: if a daemon is up they become thin clients and post messages to it, so memory, heartbeat and WhatsApp stay in one place. If nothing is running they claim the home and start their own in-process daemon. The tray uses the same backend interface in-process.

## Settings from the tray

The tray calls `Daemon.UpdateConfig(mutate)`: start from `config.yaml` as it is on disk (the live config when there is no file, so a change made with `mirrin init` meanwhile is kept), apply the change, point the voice settings at the persona where the user didn't choose their own, validate, build the new model (a provider without a key is refused here, not saved), save, record what the persona asked of the voice settings (`persona.voice.v1`, which therefore always describes the file), then swap in the new config, hand the agent its copy (`SetConfig`) and rebuild what depends on it (model provider, approvals policy, voice). Nothing restarts, and a turn already running finishes on the settings it started with; the approvals policy is read live, so turning autonomy down applies at the very next tool call. A twin that started without a usable key heals the same way before its next turn, protocol or task. Voice settings are read by each `mirrin voice` session on start, so they apply to the next session and to "Preview current voice".

## Service

`kardianos/service` installs a per-user LaunchAgent on macOS (running `mirrin tray` when the menu bar is available, since LaunchAgents live in the GUI session), a systemd user unit on Linux (wanted by `default.target`, restarting after 10 seconds) and a Windows service (both `mirrin run`, headless). The menu bar loop must own the main thread, so `tray` never goes through the service wrapper. `mirrin service install` (`service.Control`) saves the keys the service needs in `secrets.env` (see Secrets), retires the AntBot and openHuman services from before the renames (the first `run`, `tray`, `chat`, `voice`, `init` or `service` command already stops one that runs an older program, saving its keys first, so its home can move to `~/.mirrin`), replaces any earlier install so a new binary or mode takes effect, starts it (on macOS by bootstrapping into the login session and kickstarting), and waits up to 20 seconds for the twin to answer, printing the last error from `~/.mirrin/logs` if it doesn't. `status` tells installed, running and answering apart.
